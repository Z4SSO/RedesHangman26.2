1. Visão geral

O PyP2P-Forca é um cliente peer-to-peer do Jogo da Forca, em Python. Cada instância (peer) se registra em um servidor Rendezvous central, descobre os outros peers do mesmo namespace, abre conexões TCP persistentes com todos eles e, sobre essas mesmas conexões, joga forca em turnos. Em cada partida, um peer assume o papel temporário de host (conhece a palavra, valida as jogadas e difunde o estado) e os demais são jogadores. O host não joga. O modo é cooperativo: as vidas são compartilhadas.

O protocolo é o definido na especificação do professor. O projeto implementa todas as mensagens, as regras do jogo, a máquina de estados do host e do jogador, a tolerância a falhas (queda de jogador, reconexão, queda do host) e o encerramento ordenado. Também implementa o bônus de chat (mensagem CHAT, seção 7).

3. Arquitetura da solução

3.1 Duas camadas sobre as mesmas conexões TCP

                    +------------------------------+
                    |  Servidor Rendezvous         |
                    |  pyp2p.mfcaetano.cc : 8080   |
                    +---------------+--------------+
        REGISTER / DISCOVER / UNREGISTER  (uma conexão curta por comando)
        +---------------------------+---------------------------+
        |                           |                           |
  +-----v------+              +-----v------+              +-----v------+
  | alice@CIC  |              |  bob@CIC   |              | carol@CIC  |
  |   (HOST)   |              | (jogador)  |              | (jogador)  |
  +-----+------+              +-----+------+              +-----+------+
        |  malha de descoberta: HELLO, PING/PONG, GAME_LIST, BYE (todos com todos)
        |  estrela da partida:  JOIN, GAME_START, STATE, GUESS, GAME_OVER (host <-> jogador)
  • Malha de descoberta: cada peer conecta em todos os peers descobertos, faz o HELLO e mantém a conexão com PING/PONG. É por ela que se descobrem as partidas abertas (GAME_LIST).
  • Estrela da partida: as mensagens de jogo trafegam somente entre o host e cada jogador, pela conexão já existente. Não se abre segunda conexão. Os jogadores não trocam mensagens de jogo entre si: o host é a única fonte do estado.

3.3 Caminho de uma mensagem

socket --> PeerConnection --(HELLO, PING/PONG, BYE tratados aqui)--+
                |  o resto                                       |
                v                                                |
          MessageRouter.on_message(conn, msg)                    |
                |  validate_envelope --> ERROR ou descarta       |
                v                                                |
     GameHost.on_*  /  GamePlayer.on_*  --> send(peer_id, msg) --+
                                            (= PeerTable.send_to)

O jogo (game_host, game_player) fala com a rede apenas por uma função Sender injetada, e nunca importa a camada de conexão. Isso permite testar toda a lógica do jogo sem abrir um socket (com um Sender falso) e foi essencial para B e C trabalharem em paralelo com A.

3.4 Concorrência

Todo o programa roda em um único event loop asyncio: não há threads de rede nem estado compartilhado entre threads. Regras seguidas: nada bloqueia o loop (a leitura do teclado vai para uma thread própria; arquivos usam asyncio.to_thread); a escrita em cada socket é protegida por um asyncio.Lock para que duas tarefas (host, KeepAlive, CLI) não misturem as linhas; toda tarefa em segundo plano é guardada e cancelada no encerramento; uma mensagem inválida nunca derruba o programa (vira ERROR ou é descartada); e nenhum laço que fala com o Rendezvous roda sem asyncio.sleep, porque o servidor bloqueia o IP por 1 minuto acima de 50 requisições por minuto (no uso normal são cerca de 3 por minuto por peer).

3.5 Ciclo de vida de um peer

Início: sobe o servidor TCP, registra-se no Rendezvous e dispara duas tarefas periódicas: DISCOVER a cada discover_interval (20 s) → reconcilia a tabela e conecta nos novos; e refresh do registro a cada metade do TTL. Se o Rendezvous estiver fora do ar, o peer sobe mesmo assim e tenta registrar de novo a cada intervalo.

Encerramento (/quit e Ctrl+C seguem o mesmo caminho): (0) cancela as tarefas periódicas; (1) se for host com partida ativa, envia GAME_OVER ABORTED aos jogadores; (2) se for jogador em partida, envia LEAVE ao host; (3) envia BYE a todos os vizinhos e espera o BYE_OK por até 2 s; (4) UNREGISTER no Rendezvous; (5) para os PINGs e fecha o servidor TCP. Cada passo é protegido: um erro não impede os seguintes.

3.6 Máquinas de estado

Host (por partida):
  IDLE --/create--> OPEN --/start (>= 1 jogador)--> RUNNING
  em OPEN:    JOIN -> JOIN_OK | LEAVE -> LEAVE_OK | GAME_LIST -> GAME_LIST_OK | /cancel
  em RUNNING: GUESS -> GUESS_RESULT + STATE | LEAVE -> STATE
              timeout de turno -> STATE | jogador STALE -> STATE
  OPEN ou RUNNING --GAME_OVER (WON | LOST | ABORTED)--> FINISHED
  FINISHED --(anunciada por 60 s em GAME_LIST_OK)--> IDLE

Jogador:
  IDLE --/join--> JOINED --GAME_START + STATE seq=1--> PLAYING
  JOINED --JOIN_ERR ou /leave--> IDLE
  PLAYING --GAME_OVER, /leave ou host STALE--> IDLE

Peer na tabela:
  DISCOVERED -> CONNECTING -> CONNECTED -> STALE --(backoff, N tentativas)--> GONE
  GONE volta a DISCOVERED quando reaparece em um DISCOVER

4.1 Peer ↔ Rendezvous

Cada conexão TCP com o Rendezvous aceita exatamente um comando (uma linha JSON) e é fechada pelo servidor após a resposta; por isso o cliente abre uma conexão nova a cada operação, com timeout de 5 s para conectar e para ler. O formato é o do servidor (status OK/ERROR), diferente do envelope peer-to-peer; nele, ttl é o tempo de vida do registro em segundos.

REGISTER registra o peer e também renova o TTL (refresh na metade do TTL). A resposta traz o ip observado pelo servidor, a única forma de o peer conhecer seu endereço público (guardado e registrado no log, junto com o aviso de que atrás de NAT é o IP do roteador).

DISCOVER lista os peers de um namespace (ou de todos, se o campo for omitido, como no /peers *). A resposta inclui o próprio peer, por isso o cliente o filtra pelo par name + namespace antes de conectar. Se o DISCOVER falhar, a tabela não é reconciliada (senão uma falha do servidor marcaria todos como ausentes). Se o servidor responder peer_not_registered (o registro expirou), o cliente faz um novo REGISTER e repete o DISCOVER uma vez.

4.2 Peer ↔ Peer: envelope e transporte

Toda mensagem é um objeto JSON em uma linha, UTF-8, terminada em \n, com no máximo 32 KiB. Campos do envelope: type, msg_id (UUID v4), ttl (sempre 1; qualquer outro valor é descartado em silêncio), e src/dst (peer_id = nome@namespace) em todas as mensagens, exceto HELLO, HELLO_OK, PING e PONG, que são mensagens de conexão. As respostas repetem o msg_id da requisição (*_OK, JOIN_ERR, GUESS_RESULT, PONG, BYE_OK); o ERROR tem msg_id novo e aponta a causa em ref_msg_id.

A validação (em protocol.validate_envelope) confere, nesta ordem: tipo conhecido (unknown_type), msg_id e ttl, src/dst, destinatário (not_for_me), campos obrigatórios e o tipo de cada campo (bad_request). Mensagem em contexto inválido (por exemplo, GUESS sem partida) gera ERROR invalid_state. Linha que não é JSON gera ERROR bad_json e fecha a conexão. Linha maior que 32 KiB fecha só aquela conexão. O recebimento é tolerante (campos opcionais podem faltar) e o envio é rígido (todos os campos da especificação, null quando não se aplicam). O roteador ainda descarta mensagens cujo src difere do peer dono do socket (anti-spoofing).

4.3 Sessão: HELLO, desempate de duplicadas, PING/PONG e BYE

HELLO / HELLO_OK. Quem abre a conexão envia HELLO com seu peer_id, version "1.0" e features (obrigatório conter "hangman"); quem aceita responde HELLO_OK com o mesmo msg_id. Até o HELLO_OK, qualquer outra mensagem é descartada. Um peer sem a feature hangman é aceito na malha, mas nunca recebe mensagens de lobby ou de partida.

{{EX:hello}} {{EX:hello_ok}}

Conexões duplicadas. Como todos tentam conectar em todos, é comum dois peers abrirem conexão um para o outro ao mesmo tempo. Regra: vale a conexão aberta pelo peer de menor peer_id (ordem lexicográfica); a outra é fechada com BYE reason:"duplicate". Cada lado calcula isso sozinho (se meu id é menor, vale a minha conexão de saída; senão, a de entrada) e os dois chegam à mesma escolha sem conversar. A vencedora é anunciada antes de a perdedora ser fechada, e a tabela troca de conexão sem emitir peer_stale, para não derrubar uma partida por uma queda que não houve. Resultado: o /conn mostra exatamente uma conexão por vizinho.

PING / PONG. Os dois lados enviam PING a cada ping_interval (30 s). O PONG repete o msg_id e o timestamp do PING. O RTT é medido com relógio monotônico, casado por msg_id, e o valor mostrado é a média móvel dos últimos 10. Após 3 PINGs consecutivos sem PONG, o peer é marcado STALE, a conexão é fechada (com BYE reason:"idle") e o evento peer_stale dispara uma única vez; é o gatilho de falha do jogo.

{{EX:ping}} {{EX:pong}}

4.5 Partida

Regras fixadas pela especificação. O host não joga e precisa de pelo menos 1 jogador. A palavra tem 3 a 20 letras a–z, é normalizada (minúsculas, sem acentos) pelo host e o word_hash é o SHA-256 da palavra normalizada. Modo cooperativo, com vidas compartilhadas (padrão 6). Turnos em round-robin na ordem de entrada, passando ao próximo após uma jogada aceita, acertando ou não. Letra correta revela todas as ocorrências; incorreta custa 1 vida; letra repetida é rejeitada (letter_already_used). Palpite de palavra certo encerra com WON; errado custa 1 vida. Se o jogador da vez não joga em turn_timeout (30 s), o host passa o turno sem custar vida. Fim: WON (palavra completa) ou LOST (vidas esgotadas). Cada letra revelada vale 1 ponto por ocorrência. Jogada rejeitada não gera STATE nem consome o turno.

GAME_START (host → cada jogador, ao /start) traz a ordem definitiva dos turnos, as vidas, o tamanho da palavra e o word_hash, que permite ao jogador verificar depois que o host não trocou a palavra. Em seguida o host envia o primeiro STATE (seq: 1).

{{EX:game_start}}

STATE é o estado autoritativo, enviado a todos os jogadores após qualquer mudança (jogada aceita, timeout, entrada ou saída de jogador). O seq começa em 1 e cresce de 1 em 1; o jogador descarta qualquer STATE com seq menor ou igual ao último aplicado. O primeiro exemplo é uma jogada; o segundo, um timeout de turno (last_guess com timeout: true, vidas inalteradas):

{{EX:state}} {{EX:state_timeout}}

GUESS / GUESS_RESULT. O jogador envia exatamente um entre letter e word. O host responde só ao autor, repetindo o msg_id: accepted: true com correct, ou accepted: false com reason (not_your_turn, letter_already_used, invalid_letter, invalid_word, game_not_running). O efeito sobre a partida chega a todos pelo STATE seguinte.

{{EX:guess}} {{EX:guess_result}} {{EX:guess_not_your_turn}} {{EX:guess_used}}

GAME_OVER (host → todos) traz o resultado, a palavra, o vencedor (null em LOST/ABORTED) e o placar. Ao recebê-lo, o jogador calcula sha256(word) e compara com o word_hash do GAME_START; divergência é registrada como WARNING (host cheated: hash mismatch). Nos testes, o log mostra GAME_OVER WON word=... winner=... — hash OK.

Reconexão com backoff. Um peer STALE é tentado de novo após base_backoff × 2n segundos, limitado a max_backoff (com os padrões: 2, 4, 8, 16, 32 s). Depois de max_reconnect_attempts (5) tentativas sem sucesso, vira GONE até reaparecer em um DISCOVER. A espera usa asyncio.sleep em tarefa própria, então um peer em espera não atrasa os outros; conectar de novo (por nós ou pelo próprio vizinho) zera a contagem. O comando /reconnect tenta já todos os peers STALE.

5. Decisões de projeto (onde a especificação deixa margem)

As decisões foram registradas em docs/CONTRATO.md (seção 6) antes de codificar, para os três módulos concordarem. As principais:

  • Desempate de duplicadas: menor peer_id (comparação de strings), como na especificação.
  • /cancel envia GAME_OVER ABORTED com reason:"host_shutdown" (a especificação lista só host_shutdown e no_players).
  • Todo GAME_OVER passa por FINISHED: a partida fica anunciada por 60 s em GAME_LIST_OK e depois volta a IDLE. Não há STATE final na vitória/derrota: o GAME_OVER vem logo após o GUESS_RESULT.
  • Um peer, uma partida: quem cria ou entra em uma partida verifica que não está em outra; o jogo recebe um busy() para olhar o outro objeto sem importá-lo.
  • Palpite de palavra é normalizado como a palavra secreta (/word BANANA = banana).
  • Linha que não é JSON antes do HELLO só fecha a conexão, sem ERROR (o vizinho ainda não tem peer_id, e o ERROR sairia sem dst). Depois do HELLO, responde ERROR bad_json e fecha, como na especificação. É um desvio consciente do texto literal.
  • NAT e o mesmo IP público. O Rendezvous divulga o IP público de cada peer, e muitos roteadores não deixam alcançar o próprio IP público por dentro (sem hairpin NAT). Observamos isso: três peers na mesma máquina, usando o servidor público, não conseguiam se conectar. Solução: se o vizinho tem o mesmo IP público que o meu, o cliente tenta 127.0.0.1:porta primeiro e só depois o IP divulgado (se o vizinho estiver em outra máquina da mesma rede, a tentativa em 127.0.0.1 é recusada na hora).
  • Validação de configuração: discover_interval e register_ttl pequenos demais viram um laço sem pausa contra o Rendezvous (limite de 50 req/min), então são recusados na leitura do config.json.

5Letra repetida e palpite de palavraletter_already_used sem consumir o turno; /word errado custa 1 vida; /word certo encerra.
6Timeout de turnoTurn timeout for ... — skipping, STATE com timeout: true, vidas inalteradas.
7Queda de jogador7a com kill -9 (socket fechado) e 7b com SIGSTOP (processo congelado: só o KeepAlive percebe, após missed 3 PINGs). O host remove o jogador, difunde STATE e a partida continua.
8Reconexão de jogadorProcesso novo na mesma porta, /join, rejoin: true, STATE corrente, fim do rodízio.
9Queda do hostOs jogadores mostram Host ... unreachable — game aborted e voltam a IDLE.
10Encerramento limpoA ordem é comprovada pelo log Wire: GAME_OVER ABORTED (host) ou LEAVE (jogador) → BYE → UNREGISTER; também sem partida e com Ctrl+C. O processo termina sozinho, com código 0.

Observação sobre o cenário 7: em 127.0.0.1, um kill -9 faz o sistema operacional fechar o socket e a queda é vista na hora; por isso a variante com SIGSTOP, que exercita de fato a contagem de 3 PINGs.

Cenário 11 — interoperabilidade. O nosso cliente foi testado como jogador contra o bot oficial dos monitores (bot@CIC, Rendezvous público), com tools/bot_check.py: (a) vitória com 2 jogadores nossos na mesma partida, (b) derrota, e (c) jogador inativo: após 3 timeouts sem custo de vida o bot enviou BYE reason:"idle", que respondemos com BYE_OK do mesmo msg_id, e uma tentativa de voltar foi recusada com JOIN_ERR game_running, como descreve a política do bot. Em todos os casos o word_hash conferiu (hash OK) e nenhum STATE foi descartado por seq fora de ordem.

7. Bônus implementado: chat na partida

Extensão opcional CHAT, só entre peers com a feature hangman. O jogador envia CHAT {game_id, text} ao host; o host valida (partida aberta ou em andamento, mesmo game_id, autor é jogador) e repassa a todos os outros jogadores com o campo from; o host também pode falar. O texto tem no máximo 200 caracteres e quem recebe troca caracteres de controle por espaço (para um \n não forjar linhas de log). Um cliente sem suporte responde ERROR unknown_type, que é apenas registrado, e a conexão segue. O comando é /chat <texto>.

8. Limitações conhecidas

  • Cliente de referência: o pyp2p-forca citado na especificação não foi disponibilizado. A interoperabilidade foi testada com o bot oficial, mas o nosso cliente como host contra um cliente de terceiros não foi exercitado; o papel de host foi testado contra os nossos próprios jogadores (cenários 2 a 10).
  • NAT: peers em redes diferentes só se alcançam se a porta de escuta estiver acessível (encaminhamento de porta); o Rendezvous só divulga o IP público. Todos os testes foram executados em uma única máquina; entre máquinas diferentes não foi testado.
  • Desvio consciente: ERROR não é enviado para linha não-JSON anterior ao HELLO (seção 5).
  • Os demais bônus da especificação (migração de host, modo competitivo, múltiplas partidas) não foram incluídos nesta entrega.

9. Divisão do trabalho e organização

O trabalho foi dividido em três trilhas com donos de módulo (tabela da seção 0), definidas a partir de um contrato de interfaces (docs/CONTRATO.md) acordado e congelado antes de codificar: assinaturas, quem trata cada tipo de mensagem, decisões onde a especificação deixa margem e a ordem de encerramento. O fluxo combinado foi: um branch por tarefa, revisão cruzada por outro integrante (A revisa B, B revisa C, C revisa A) e merge por pull request. As ferramentas de apoio (tools/) permitem reproduzir todos os cenários descritos aqui.
